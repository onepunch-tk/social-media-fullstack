# ADR-003: 검증 분담: zod = 와이어 계약, class-validator = API 입구

## Status
Accepted (2026-09-16)

## Context
사용자가 zod(공통 스키마)와 class-validator/class-transformer(Nest DTO)를 모두 요구했고(PRD §12.3, §12.4), 둘 다 쓰면 검증 책임이 겹친다. 대안: (a) zod를 packages에 두고 class-validator DTO는 api presentation에만 둔다 (b) `packages/dto`로 class-validator 클래스도 공유한다 (c) `nestjs-zod`로 DTO를 파생한다. 관련: ADR-002(패키지 포맷).

## 결정
(a)를 채택한다.
- `packages/schemas`의 zod 스키마 + 추론 타입이 유일한 와이어 계약이며 모바일·API가 함께 소비한다.
- class-validator DTO 클래스는 `apps/api` presentation의 `dtos/`에만 두고 zod 추론 타입을 `implements`한다.
- 모바일은 `zod`를 직접 import하지 않고 `@social/schemas`만 import한다.

## 이유
- 모바일 번들에 데코레이터·reflect-metadata 의존이 들어가지 않는다.
- Nest의 `ValidationPipe`(whitelist/forbidNonWhitelisted/transform) 관용구를 그대로 쓴다.
- `implements`로 필드 누락·타입 드리프트가 tsc에서 잡힌다.
- Metro에서 zod가 두 복사본으로 로드되면 instanceof 기반 검사가 깨지므로 import 경로를 하나로 묶는다.

## 트레이드오프
- 런타임 규칙(길이·enum 등)이 zod와 데코레이터에 이중 선언되어 수동 동기화가 필요하다 — 자동 보장은 타입 수준뿐이다.
- (c)는 중복이 0이지만 사용자가 명시한 class-validator를 사실상 제거하므로 채택하지 않았다.
